# PillPal API & Database

Backend for **PillPal**, the smart pill dispenser (Capstone team M1). It is the piece in the
middle that the React Native companion app and the Raspberry Pi hub both talk to:

```
                       ┌──────────────────────────────┐
  React Native app ───▶│        PillPal API            │◀─── Raspberry Pi 5 hub
  (Iris)               │  Node.js · Express · Prisma   │     (Henry)  5 servos / IR break beams
  /api/v1/...          │                               │     /api/v1/device/...   load cell · BP cuff
                       │  ┌─────────────────────────┐  │
                       │  │  scheduler job (60 s)    │  │   • generates doses from schedules
                       │  │  automated notifications │  │   • reminders · missed-dose alerts
                       │  └─────────────────────────┘  │   • low stock · device offline · vitals
                       └──────────────┬────────────────┘
                                      ▼
                               PostgreSQL (Prisma)
```

**What it does**

* Accounts, login tokens, caregiver sharing
* Medications, the 5 hopper slots of a dispenser, pill inventory + refill history
* Schedules ("08:00 every day", "Mon/Wed/Fri") → concrete dose events with a full history
* Device pairing with a 6-character claim code, sync endpoint for the Pi, remote commands (dispense now, ring, calibrate…)
* Vitals (blood pressure from the BLE cuff, etc.) with out-of-range alerts
* **Automated notifications**: dose reminders, missed doses (also to caregivers), low stock, device offline, dispense failures — stored in-app and pushed to the phone via Expo

## Tech stack (and why)

| Piece | Choice | Why |
|---|---|---|
| Runtime / language | Node.js 20+ · TypeScript | Same language as the React Native app; huge ecosystem |
| Web framework | Express 5 | Most widely documented; v5 handles `async` errors natively |
| Database | PostgreSQL 16 | Free tiers everywhere (Neon, Supabase, Railway, Render); rock solid |
| ORM / migrations | Prisma 7 | Schema in one readable file (`prisma/schema.prisma`), type-safe queries, visual DB browser (`npm run db:studio`) |
| Validation | zod | Every request body is validated; bad input returns a clear 400 |
| Auth | JWT + refresh tokens (app) · API keys (device) | Standard, stateless, works from a phone and a Pi |
| Push | expo-server-sdk | Matches an Expo / React Native app |
| Tests | vitest + supertest | 22 tests cover the whole Pi ↔ app flow |

## Prerequisites

1. **Node.js 20 or newer** (LTS) – https://nodejs.org  → check with `node -v`
2. **VS Code** with the recommended extensions (VS Code will prompt you when you open the folder; they are listed in `.vscode/extensions.json`: Prisma, Prettier, REST Client, Docker, Vitest)
3. **A PostgreSQL database** – pick ONE:
   * **Docker Desktop** (recommended): https://www.docker.com/products/docker-desktop → then `npm run db:up` starts Postgres for you
   * **Free cloud Postgres**: create a project on https://neon.tech (or Supabase/Railway), copy the connection string into `.env` as `DATABASE_URL`. Everyone on the team can share it.
   * **Local install**: https://www.postgresql.org/download/ → create a database called `pillpal` and put `postgresql://postgres:<password>@localhost:5432/pillpal` in `.env`

## Quick start

```bash
# 1. open the folder in VS Code (File → Open Folder → pillpal-api), then in the VS Code terminal:
npm install                 # installs packages and generates the Prisma client
cp .env.example .env        # Windows PowerShell: copy .env.example .env
npm run db:up               # starts PostgreSQL in Docker (skip if you use Neon / a local install)
npm run db:migrate          # creates all tables from prisma/migrations (says "already in sync" when nothing is new)
npm run db:seed             # demo account, dispenser, medications, 2 weeks of history
npm run dev                 # API on http://localhost:4000  (restarts on every save)
```

Open http://localhost:4000/api/v1/health – you should see `{"status":"ok","database":"ok"}`.

Then open `requests.http` in VS Code and click **Send Request** above the blocks to walk through the whole API
(login → dashboard → medications → claim a dispenser → Pi sync → report a dose …).

**Demo logins** (seeded): `demo@pillpal.app` / `Password123!` (patient), `caregiver@pillpal.app` / `Password123!` (caregiver).
**Demo device key** (for the Pi endpoints): `pp_dev_demo_0000000000000000000000000000000000000000`.

Browse the data visually any time with `npm run db:studio` (Prisma Studio, opens in the browser).

## How the pieces fit together

### Dose lifecycle

```
            scheduler job            Pi dispenses             user/Pi confirms
Schedule ───────────────▶ SCHEDULED ──────────────▶ DISPENSED ─────────────────▶ TAKEN
("08:00 daily")               │                        │
                              │ window closes          │ window closes
                              ▼                        ▼
                            MISSED ◀───────────────────┘        SCHEDULED ─▶ SKIPPED (user)
                                                                 SCHEDULED ─▶ FAILED  (jam / empty) ─▶ DISPENSED (retry)
```

* Every minute the scheduler turns active schedules into `dose_events` for the next 48 h (idempotent – no duplicates).
* Times are stored as `"HH:MM"` plus the user's IANA timezone, so daylight saving is handled correctly.
* By default a dispensed dose counts as taken. Turn on `requireTakenConfirmation` in notification settings if the
  tray sensor / touchscreen should confirm first.
* `graceMinutes` (per schedule, default 60) decides when a dose becomes **MISSED**.

### Automated notifications (`src/jobs/scheduler.ts`)

| Type | When | Who |
|---|---|---|
| `DOSE_REMINDER` | at scheduled time (minus `reminderLeadMinutes`), respects quiet hours | patient |
| `DOSE_MISSED` | grace window closed without TAKEN | patient + caregivers |
| `LOW_STOCK` | slot count ≤ medication `refillThreshold` (once per refill) | patient + caregivers |
| `DEVICE_OFFLINE` / `DEVICE_ONLINE` | no sync for `DEVICE_OFFLINE_AFTER_MINUTES` (5) | patient + caregivers |
| `DEVICE_ERROR` | Pi reports a failed dispense | patient + caregivers |
| `VITALS_ALERT` | reading outside safe range (e.g. BP ≥ 180/120) | patient + caregivers |

Every notification is saved in the `notifications` table (the app's inbox) and pushed to any Expo push token the
user registered. Users can switch each category off in `PATCH /api/v1/notifications/settings`.
You can trigger the job by hand with `POST /api/v1/system/tick` (header `X-Admin-Key`).

### Device (Raspberry Pi) flow

1. First boot: `POST /device/register` with the shared `X-Provisioning-Key` → API key (save it!) + 6-char **claim code**
2. Pi shows the claim code on the touchscreen and polls `GET /device/claim-status`
3. User enters the code in the app → `POST /devices/claim` → the device belongs to that user
4. Pi calls `POST /device/sync` every 30 s: sends a heartbeat (+ load-cell weights), receives slots, medications,
   schedules, the upcoming dose list (with ids) and pending commands → it can run fully offline until the next sync
5. Pi reports `POST /device/doses/:id/dispensed` (break-beam count), `/taken`, `/failed`; uploads vitals/readings/logs
6. App can queue commands (`DISPENSE`, `RING`, `TARE_SCALE`, …) → delivered in the next sync → Pi reports `/commands/:id/complete`

See **docs/PI_INTEGRATION.md** and `examples/pi_client.py`.

## Changing the database

1. Edit `prisma/schema.prisma` (the Prisma VS Code extension gives autocomplete and formatting)
2. `npm run db:migrate` → name the migration (e.g. `add_dose_notes`) → Prisma writes the SQL into `prisma/migrations/` and applies it
3. The generated TypeScript client updates automatically, so wrong field names fail at compile time
4. Commit the migration folder so teammates get the same change with `npm run db:migrate`

## Deploying (so the Pi and phones can reach it from anywhere)

The simplest free path: **Neon** (database) + **Render** (API).

1. https://neon.tech → New project → copy the connection string
2. https://render.com → New → Web Service → connect your GitHub repo
   * Build command: `npm install && npm run build && npx prisma migrate deploy`
   * Start command: `npm start`
   * Environment: `DATABASE_URL` (from Neon), `JWT_SECRET` (long random string), `DEVICE_PROVISIONING_KEY`, `ADMIN_API_KEY`, `NODE_ENV=production`
3. Point the Pi (`PILLPAL_API`) and the app (`BASE_URL`) at `https://<your-service>.onrender.com/api/v1`

Railway and Fly.io work the same way. (`render.yaml` in the repo describes this setup for Render's "Blueprint" button.)

For LAN testing during development: run `npm run dev`, find your laptop's IP (`ipconfig` / `ifconfig`), and use
`http://<laptop-ip>:4000/api/v1` from the phone and the Pi (same Wi-Fi, firewall must allow port 4000).

## Troubleshooting

| Symptom | Fix |
|---|---|
| `Can't reach database server at localhost:5432` | Postgres isn't running: `npm run db:up` (Docker Desktop must be open) or check `DATABASE_URL` in `.env` |
| `password authentication failed` | The user/password in `DATABASE_URL` doesn't match your Postgres. For Docker it's `pillpal` / `pillpal` |
| `EADDRINUSE: address already in use :::4000` | Another process uses port 4000 – stop it or set `PORT=4001` in `.env` |
| `Error: @prisma/client did not initialize` / missing `src/generated` | Run `npm run db:generate` (happens automatically on `npm install`) |
| `npm install` fails while Prisma downloads its engine (`binaries.prisma.sh`) | Some campus/corporate networks block it – retry on another network / hotspot, or set `PRISMA_ENGINES_MIRROR` to a mirror |
| `prisma migrate dev` complains about a shadow database (cloud DBs) | Use `npm run db:push` for development, or set `shadowDatabaseUrl` in `prisma.config.ts` |
| Phone/Pi can't reach the API on the laptop | Use the laptop's LAN IP, not `localhost`; allow port 4000 in the firewall; same Wi-Fi network |
| `npm audit` shows vulnerabilities | They are inside the Prisma **CLI** dev tooling (mysql2 etc.), not in the running server. Don't run `npm audit fix --force` – it downgrades Prisma |
| Tests fail with "database does not exist" | The test DB is created by `prisma db push` in `tests/globalSetup.ts`; make sure Postgres is running and the user may create databases |

## Security notes (for the report)

* Passwords are hashed with bcrypt; refresh tokens and device API keys are stored only as SHA-256 hashes
* Access tokens are JWTs (1 day) with 30-day rotating refresh tokens; login endpoints are rate-limited
* Devices authenticate with a per-device key issued once at registration; claim codes expire after 30 minutes
* Every query is scoped to the authenticated user (a user can never read another user's data – covered by tests)
* `helmet` sets secure HTTP headers; request bodies are validated with zod before touching the database
